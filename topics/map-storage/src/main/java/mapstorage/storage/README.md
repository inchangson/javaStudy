# 캐시에서 작은 저장소로, 그리고 RDB 트랜잭션으로

[캐시](../cache/README.md)는 원본에서 재생성할 수 있는 값을 보관한다고 보았다.
이제 Map을 잔액의 기준 상태로 사용한다고 가정한다. 값이 빨리 조회되는 것 외에,
여러 변경의 성공·실패와 독자의 관찰, 재시작 후 복구를 보장해야 한다.

## 같은 이체에 서로 다른 실패를 넣어 보기

```text
시작                  A=1000, B=1000
A에서 100 차감        A=900,  B=1000
B에 100 입금          A=900,  B=1100
```

| 차감 직후 발생한 일 | 필요한 성질 | 구현과 관찰 |
| --- | --- | --- |
| 다른 스레드가 합계를 읽음 | 이체 중간 상태를 관찰하지 않게 할 경계 | [concurrency](../concurrency/README.md)의 합계 1900 → atomic의 snapshot 차단 |
| JVM은 살아 있지만 처리 중 예외 발생 | 두 변경을 모두 적용하거나 되돌리기 | [atomic](atomic/README.md)의 이전 값 보관과 롤백 |
| 프로세스 강제 종료 | 메모리 밖 기록으로 커밋 판정과 복구 | [recovery](recovery/README.md)의 커밋 전후 종료 실험 |

AtomicBalances는 이체와 snapshot 모두 같은 모니터를 사용한다.
작성자만 잠그고 독자가 직접 Map을 읽게 하면 중간 상태를 숨길 수 없다.
또 잠금만으로 이전 값을 복구할 수 없고, catch의 롤백만으로 프로세스 종료를 복구할 수도 없다.
그래서 메모리 원자성 실험과 WAL 복구 실험을 별도 구현으로 둔다.

## RDB 트랜잭션과 비교하기

아래 표는 개념의 대응이다. AtomicBalances/WalBalances가 실제 DB의 내부 구현과 같다는 뜻은 아니다.
RDB 비교의 구체적인 기준은 PostgreSQL 18 문서다.

| 질문 | 현재 실험 | RDB에서 이어서 볼 개념 |
| --- | --- | --- |
| 작업 일부만 남지 않게 하려면? | 이전 잔액 보관, 예외 시 복구 | 트랜잭션의 원자성, COMMIT/ROLLBACK |
| 합계와 잔액 규칙을 어떻게 지킬까? | 금액·잔액·오버플로 검증, 합계 보존 | 일관성: 제약조건과 애플리케이션의 업무 규칙 |
| 독자는 어떤 상태를 볼까? | 이체와 snapshot에 공통 모니터 | 격리 수준, MVCC, 잠금 |
| 성공한 변경을 장애 후 어떻게 살릴까? | 커밋 프레임 기록·force·redo | 내구성, WAL, 복구 |

원자성(A), 일관성(C), 격리성(I), 내구성(D)은 각각 다른 질문이다.
일관성은 캐시의 최신성과 같은 뜻으로 쓰지 않는다. 트랜잭션을 열었다고 업무 규칙이
자동으로 만들어지는 것도 아니다. 이체 금액 검증이나 제약조건을 별도로 설계해야 한다.

[PostgreSQL 트랜잭션 설명](https://www.postgresql.org/docs/18/tutorial-transactions.html)은
여러 SQL을 BEGIN/COMMIT으로 묶고 ROLLBACK으로 취소하는 이체 예제를 제공한다.
우리 두 put과 대응시킬 수 있지만, 현재 패키지는 실제 DB 연결·SQL 실행을 구현하지 않는다.

[PostgreSQL 격리 수준 설명](https://www.postgresql.org/docs/18/transaction-iso.html)을 읽을 때는
“독자가 무조건 작성자의 잠금 해제를 기다린다”로 일반화하지 않는다.
PostgreSQL의 기본 Read Committed에서 일반 SELECT는 쿼리 시작 시점의 커밋된 상태를 본다.
같은 트랜잭션의 연속된 두 SELECT도 다른 트랜잭션의 커밋 때문에 다른 결과를 볼 수 있다.
우리 snapshot의 모니터 모델을 RDB의 MVCC나 모든 격리 수준과 동일시하지 않는다.

[PostgreSQL WAL 설명](https://www.postgresql.org/docs/18/wal-intro.html)은 데이터 파일 반영보다
로그의 영속화를 앞세워 장애 시 redo할 수 있게 하는 원리를 설명한다.
우리 WalBalances는 별도 데이터 파일 없이 로그 전체에서 Map을 복원하는 작은 모델이다.
실제 DB의 페이지·체크포인트·복구 구현 전체를 재현한 것은 아니다.

## 현재 검증한 것과 다음 RDB 실습

현재 테스트는 다음을 직접 검증한다.

- concurrency: get+put의 증가 유실, 두 compute 사이의 중간 잔액.
- atomic: 예외 시 잔액 복구, 입력 검증, 이체 중 독자의 snapshot 차단.
- recovery: 커밋 전후 프로세스 강제 종료, 커밋된 상태의 재복구.

다음 RDB 실습은 별도로 진행한다. 이 문서의 설명만으로 검증이 끝난 것은 아니다.

1. A/B 행을 만들고 두 UPDATE를 한 트랜잭션으로 묶어 COMMIT과 ROLLBACK을 비교한다.
2. 두 DB 세션에서 작성 중인 잔액을 읽어 일반 SELECT와 잠금 읽기의 차이를 확인한다.
3. 같은 데이터를 두 번 읽으며 Read Committed와 Repeatable Read의 관찰 차이를 확인한다.
4. 동일 계좌를 동시에 갱신하며 갱신 유실 방지, 잠금 순서, 교착과 재시도를 공부한다.
5. DB 커밋 후 캐시 무효화 전에 프로세스가 종료되는 상황을 그려 본다.
   DB 트랜잭션만으로 외부 메모리 캐시까지 원자적으로 갱신되지 않는 이유를 설명한다.

HashMap의 버킷 트리와 TreeMap은 이 실습의 선행 조건이 아니다.
지금은 “어떤 상태를 누가 언제 보고, 어느 실패 이후에 무엇이 남는가”를 따라가면 된다.
